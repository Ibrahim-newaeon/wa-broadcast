1.Architecture & stack

LayerTechnology
Web / appNext.js 15 (App Router), React Server Components
LanguageTypeScript strict (noUncheckedIndexedAccess)
DataPrisma + PostgreSQL
Queue / jobsBullMQ + Redis (send queue + recurring scheduler)
Authjose (JWT) + bcryptjs — access edge-verified, refresh stateful in Redis
ValidationZod (every API body / CSV row / webhook payload)
TestsVitest (unit), Playwright (e2e)
DeployDocker / Railway — two processes from one image: web + worker
ExternalMeta WhatsApp Cloud API (Graph API)

Process model: web serves UI + API and enqueues sends; worker consumes the rate-limited send queue, runs the recurring/drip scheduler, and does boot-time sync.

Edge boundary: middleware.ts verifies the access token only (no Redis/DB/Prisma at the edge). Refresh rotation + revocation happen only in the Node runtime.

I.V1 — existing features built & live

1.1 · Authentication & sessions

  • Email + password login; bcrypt-hashed (cost 12).
  • Split-token model: short-lived stateless access token (edge-verified) + stateful refresh token (jti + version in Redis), rotated every refresh, revocation-checked only in /api/auth/refresh. Role + client id ride in the access claims.
  • Logout + logout-all (bumps token version to invalidate all refresh tokens).
  • Bootstrap SUPERADMIN via seed script; DB-backed thereafter.
  • Login rate limiting (Redis fixed-window, fails open); client wrapper does one-shot silent refresh on 401.

1.2 · Multi-tenancy (Phase 3 — complete)

  • Client model + clientId on every entity; all data & routes scoped per client.
  • Pure tenant resolver: a SUPERADMIN's acting-client cookie (acid) overrides their own cid; regular users hard-pinned.
  • Super-admin client switcher + Clients management (create / switch / cascade delete).
  • Per-client uniqueness (phone, template name+language), per-client WhatsApp config, per-client webhook signature verification (routed by WABA id).
  • Provision admin login on client create (2026-06-29) — optional admin email + password (blank → strong 16-char auto-generated), creates the tenant's first ADMIN, shows credentials once; email uniqueness checked before the tenant is created.

1.3 · Contacts

  • CSV import (Zod-validated, phone-normalized) with an auto-snapshot before import.
  • Single add, inline edit, bulk delete.
  • Custom attributes (JSON) usable as template variables.
  • Delete is FK-RESTRICT when broadcast history exists.

1.4 · Lists

  • Lists + membership join; restorable snapshots (manual or pre-import) with one-click restore.
  • Unique list names per client (2026-06-29) — case-insensitive 409 + DB unique index (migration 0015 with defensive dedupe).

1.5 · Templates

  • No-code builder → submit to Meta; cached with returned status. Sync from Meta pulls statuses (now surfaces Meta's real error).
  • Variables {{1}}…; media-header (P0) IMAGE/DOCUMENT/VIDEO via Resumable Upload; template-status webhook (P1) auto-syncs approval/rejection.
  • Rich templates (Phase 5): done coupon copy-code · done carousel (2–10 cards) · todo LTO, auth/OTP, catalog, Flows.

1.6 · Broadcasts

  • Send-now or schedule; audience = a list (opt-outs excluded).
  • Per-recipient variable mapping; live delivery funnel (queued→sent→delivered→read→failed) + button-click tracking.
  • Retry failed re-enqueues only failures; rate-limited worker honoring the Meta tier.

1.7 · Recurring / drip campaigns

  • RecurringCampaign + BullMQ cron scheduler (UTC).
  • Each tick spawns a fresh broadcast from template + list, honoring opt-outs.
  • Presets + raw 5-field cron; boot-time reconcile.

1.8 · Two-way inbox (Phase 4 — complete)

  • Conversation/Message models; inbound capture for text, image, document, audio, video, sticker, interactive, reaction, location — idempotent on wamid.
  • 24-hour service-window tracking; outbound text + attachments within the window.
  • Media rendering via a token-safe proxy (/api/media/:id); read receipts (best-effort); live two-pane /inbox.

1.9 · Opt-outs & compliance

  • STOP → OptOut (unique per client+phone); excluded from all future broadcasts.
  • Opt-in consent trusted from CSV (not yet structurally enforced → V2 §2.11).

1.10 · No-code WhatsApp setup

  • Per-client Phone number ID, WABA ID, App ID, token, app secret, verify token, API version.
  • Test connection; webhook URL + verify token; saved settings override env with no redeploy.
  • Field labels clarified to avoid the WABA-vs-Business-Portfolio-id mix-up.

1.11 · Platform & ops

  • Health endpoint; security headers; multi-stage non-root Docker image with healthcheck.
  • Hand-written SQL migrations 0001 → 0015 applied on boot; offline verify.sh; k6 webhook load test; bilingual tutorial at /tutorial.html.

II.V2 — Phase 2 features

Each feature lists What · How it works · Data model · Dependencies · Effort · Acceptance. Effort assumes the existing stack.

★ 2.1 · Omnichannel inbox (WhatsApp + Instagram DM + Messenger)

What: extend the two-way inbox beyond WhatsApp to all Meta messaging surfaces in one unified agent view.

How: add a channel enum to Conversation/Message; generalize the webhook handler (route by object + connected asset) and a thin per-channel send adapter over whatsapp.ts; channel filter + badge in /inbox.

Data: Conversation.channel, Message.channel, ChannelConnection. Deps: IG Messaging + Messenger permissions.

Acceptance: an IG DM and a Messenger message appear next to WhatsApp, are replyable, and respect each window.

Effort: LFit: HighYour headline ask

★ 2.2 · Meta Embedded Signup (one-click WhatsApp onboarding)

What: replace manual Phone/WABA/token entry with Meta's Embedded Signup OAuth flow — a "Connect WhatsApp" button.

How: launch the Embedded Signup popup, exchange the code server-side for a long-lived system-user token, auto-discover WABA + phone-number ids, persist to per-client config.

Why: directly removes the #1 onboarding friction (the WABA-vs-portfolio-id confusion + token scopes). Enables true self-serve onboarding.

Data: WhatsAppConfig.wabaAutoConnected/tokenExpiresAt. Deps: Tech-Provider config + app review.

Effort: MFit: HighRecommended first

★ 2.3 · Team collaboration in the inbox

What: turn the inbox into a real shared helpdesk.

How: conversation status (OPEN/PENDING/CLOSED), agent assignment + filters, internal notes + @mentions, canned replies/snippets, SLA timers.

Data: Conversation.status/assigneeId, InternalNote, CannedReply.

Effort: MFit: High

2.4 · AI assist (Claude-powered)

What: an AI layer over conversations + content — suggested replies, conversation summary, AR↔EN translation, intent/sentiment tags, FAQ auto-answer from a per-client knowledge base, draft-broadcast copy.

How: server-side calls to the latest Claude model via the Anthropic SDK; per-client KB retrieved (RAG); agent-in-the-loop by default, optional auto-responder mode.

Data: KnowledgeDoc, Message.aiTags, Conversation.aiSummary.

Effort: MBilingual EN/AR

2.5 · Automation, auto-replies & Flows

What: 24/7 deflection + lead capture — business-hours & away messages, keyword auto-responders, a simple no-code flow builder, native WhatsApp Flows (in-chat forms), window reopen via template.

How: a rules engine in the worker on inbound events; Flows submitted to Meta like templates.

Data: AutomationRule, Flow.

Effort: L

2.6 · Contact 360 / CRM-lite

What: a unified contact profile — full cross-channel timeline (conversations + broadcasts), tags, custom-attribute editor, notes, consent + window status.

Data: Contact.tags, ContactNote.

Effort: M

2.7 · Dynamic segmentation, A/B testing & send-time

What: dynamic segments (auto-membership by rules), A/B-test broadcasts (split + compare), send-time throttling and later per-contact timezone optimization.

Data: Segment, Broadcast.variantOf.

Effort: M

2.8 · Growth & lead capture

What: wa.me deep-link + QR-code generator (prefilled + tracked), embeddable website chat widget, Click-to-WhatsApp ad attribution.

Data: Contact.source, Conversation.referral.

Effort: M

2.9 · Analytics, link tracking & deliverability

What: per-recipient link-click tracking (URL shortener), conversion/ROI reporting, exportable reports, number-quality + messaging-limit dashboard with auto-pause on quality drop, template performance.

Data: ShortLink, LinkClick, QualitySnapshot.

Effort: M

2.10 · Commerce

What: WhatsApp catalog / product / multi-product messages, order + shipping notifications, abandoned-cart flows, payment links.

Data: Catalog, Product, Order. Deps: Meta Commerce catalog + payment provider.

Effort: L

2.11 · Governance: RBAC, audit log & consent

What: per-action RBAC (beyond today's auth-only), audit log with actor attribution on broadcasts/deletions/config, double opt-in, consent log + GDPR export/delete.

Data: AuditEvent, ConsentRecord, richer Role/Permission.

Effort: MCloses V1 gaps

2.12 · Billing & self-serve (SaaS track)

What: usage metering (conversation-based, mirroring Meta), plans/quotas, Stripe billing, in-app upgrade, per-client usage dashboard. Pairs with Embedded Signup for fully self-serve onboarding.

Data: Subscription, UsageRecord, Plan. Deps: Stripe.

Effort: L

2.13 · Integrations & public API

What: outbound webhooks (message/broadcast events), Zapier/Make app, documented public REST API with per-client keys, CRM/Sheets sync.

Data: ApiKey, OutboundWebhook.

V.Non-functional requirements

  • Security: keep middleware.ts edge-safe; Zod-validate all new bodies/webhooks; extend per-client signature verification to every channel; secrets in per-client config, never committed.
  • Multi-tenancy: every new entity carries clientId; always scope via the tenant resolver; respect the SUPERADMIN acting-client override.
  • Deliverability: keep WA_MPS × workers ≤ Meta tier; quality monitoring to avoid throttling/bans.
  • Compliance: double opt-in + consent logs before scaling outbound; honor opt-outs across all channels.
  • Done gate (unchanged): typecheck · test · build all green; positive + negative tests for new logic; e2e for new routes. Migrations continue from 0016.

VI.Known limitations & open items

  • Authorization mostly authentication-only; only /api/users role-gated → §2.11 RBAC.
  • No actor attribution / audit log on broadcasts or deletions → §2.11 Audit.
  • Opt-in consent trusted from CSV, not structurally enforced → §2.11 Consent.
  • Contact delete is a no-op when broadcast history exists (FK RESTRICT).
  • Access-token revocation lags ≤15 min by design; login rate-limit fails open.
  • Per-worker rate limiting: N workers can exceed the Meta tier — keep WA_MPS × workers ≤ tier.
  • Live verification: connection + template submit/sync verified; a full broadcast + inbox round-trip on a real number is the immediate next validation (VERIFY.md).
Phase 5 (rich templates) remaining from V1 also stands: limited-time-offer → authentication/OTP → catalog → Flows (catalog & Flows now folded into V2 §2.10 / §2.5).
