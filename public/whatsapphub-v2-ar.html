واتساب هَب — مواصفات الإصدار الثاني

منصّة مراسلة متعدّدة العملاء (multi-tenant) ذاتية الاستضافة مبنية على واجهة Meta Cloud API. هذا المستند هو المرجع الكامل والمفصّل لكلّ ما يقوم به النظام اليوم (الإصدار الأول) إضافةً إلى كلّ ما هو مخطَّط للمرحلة الثانية (الإصدار الثاني) — في تحوّل من أداة بثٍّ جماعي إلى منصّة تفاعل محادثاتي متكاملة.

العلامة: NazzilVideo آخر تحديث 2026-06-29 الإصدار الأول يعمل ومستقر Next.js 15 · Prisma · BullMQ · Redis

1.البنية التقنية والمكوّنات

الطبقةالتقنية
الويب / التطبيقNext.js 15 (App Router)، مكوّنات React على الخادم
اللغةTypeScript الصارمة (noUncheckedIndexedAccess)
قاعدة البياناتPrisma + PostgreSQL
الطوابير / المهامBullMQ + Redis (طابور الإرسال + مجدول المهام المتكرّرة)
المصادقةjose (JWT) + bcryptjs — رمز الوصول يُتحقَّق منه عند الحافة، ورمز التجديد محفوظ في Redis
التحقّقZod (لكلّ طلب API / صفّ CSV / حمولة webhook)
الاختباراتVitest (وحدات)، Playwright (طرف لطرف)
النشرDocker / Railway — عمليتان من صورة واحدة: web و worker
خارجيMeta WhatsApp Cloud API (Graph API)

نموذج العمليات: تخدم عملية web الواجهة وواجهة API وتضيف الإرسالات إلى الطابور؛ بينما تستهلك عملية worker طابور الإرسال المحدود بالمعدّل، وتشغّل مجدول الحملات المتكرّرة، وتُجري المزامنة عند الإقلاع.

حدود الحافة: يتحقّق middleware.ts من رمز الوصول فقط (دون Redis أو قاعدة بيانات عند الحافة). يجري تدوير رمز التجديد والتحقّق من إبطاله في بيئة Node فقط.

أولاً.الإصدار الأول — الميزات الحالية مبنية وتعمل

1.1 · المصادقة والجلسات

  • تسجيل دخول بالبريد وكلمة المرور؛ كلمات المرور مُشفّرة بـ bcrypt (تكلفة 12).
  • نموذج الرمزين: رمز وصول قصير العمر عديم الحالة (يُتحقَّق منه عند الحافة) + رمز تجديد ذو حالة (jti + إصدار في Redis)، يُدوَّر مع كلّ تجديد، ويُتحقَّق من إبطاله فقط في /api/auth/refresh. يحمل الرمز الدور ومعرّف العميل.
  • تسجيل خروج + تسجيل خروج من كلّ الأجهزة (يرفع إصدار الرمز لإبطال كلّ رموز التجديد).
  • مشرف أوّلي عبر سكربت التهيئة؛ بعدها تعتمد المصادقة كلّياً على قاعدة البيانات.
  • تحديد معدّل لتسجيل الدخول (نافذة ثابتة في Redis، يفشل مفتوحاً)؛ يقوم غلاف العميل بتجديد صامت لمرّة واحدة عند 401.

1.2 · تعدّد العملاء (المرحلة الثالثة — مكتملة)

  • نموذج Client + حقل clientId على كلّ كيان؛ كلّ البيانات والمسارات معزولة لكلّ عميل.
  • محلّل عملاء نقيّ: يتجاوز كوكي العميل النشط (acid) لدى المشرف العام معرّفه الخاصّ (cid)؛ أمّا المستخدمون العاديون فمثبّتون على عميلهم.
  • مبدّل العملاء للمشرف العام + إدارة العملاء (إنشاء / تبديل / حذف متسلسل).
  • تفرّد لكلّ عميل (الهاتف، اسم القالب + اللغة)، وإعداد واتساب لكلّ عميل، والتحقّق من توقيع الـ webhook لكلّ عميل (يُوجَّه عبر معرّف WABA).
  • إنشاء حساب دخول للمشرف عند إنشاء العميل (2026-06-29) — بريد مشرف اختياري + كلمة مرور (فارغة ← تُولَّد كلمة قويّة من 16 خانة)، يُنشئ أوّل مستخدم ADMIN للعميل ويعرض البيانات مرّة واحدة؛ يُتحقَّق من تفرّد البريد قبل إنشاء العميل.

1.3 · جهات الاتصال

  • استيراد CSV (مُتحقَّق منه بـ Zod، الأرقام مُطبَّعة) مع نسخة احتياطية تلقائية قبل الاستيراد.
  • إضافة فردية، تعديل مباشر، حذف جماعي.
  • سمات مخصّصة (JSON) قابلة للاستخدام كمتغيّرات في القوالب.
  • الحذف مقيَّد بـ RESTRICT عند وجود سجلّ بثّ سابق.

1.4 · القوائم

  • قوائم + جدول عضوية؛ لقطات قابلة للاستعادة (يدوية أو قبل الاستيراد) مع استعادة بنقرة واحدة.
  • أسماء قوائم فريدة لكلّ عميل (2026-06-29) — تحقّق غير حسّاس لحالة الأحرف يُعيد 409 + فهرس فريد في قاعدة البيانات (الترحيل 0015 مع إزالة تكرار وقائية).

1.5 · القوالب

  • مُنشئ بدون كود ← يُرسَل إلى Meta للموافقة؛ يُخزَّن محلياً بالحالة المُعادة. المزامنة من Meta تجلب الحالات (وتُظهر الآن خطأ Meta الحقيقي).
  • متغيّرات {{1}}…؛ ترويسة وسائط (P0) صورة/مستند/فيديو عبر الرفع المتواصل؛ webhook حالة القالب (P1) يزامن الموافقة/الرفض تلقائياً.
  • القوالب الغنية (المرحلة الخامسة): منجز كوبون نسخ-الكود · منجز كاروسيل (2–10 بطاقات) · قادم عرض محدّد المدّة، مصادقة/OTP، كتالوج، Flows.

1.6 · عمليات البثّ

  • إرسال فوري أو مجدول؛ الجمهور = قائمة (مع استثناء المنسحبين).
  • ربط متغيّرات لكلّ مستلِم؛ قمع تسليم حيّ (في الطابور ← مُرسَل ← مُسلَّم ← مقروء ← فاشل) + تتبّع نقرات الأزرار.
  • إعادة محاولة الفاشل تعيد إضافة الفاشلين فقط؛ عامل محدود المعدّل وفق فئة Meta.

1.7 · الحملات المتكرّرة / بالتنقيط

  • RecurringCampaign + مجدول cron عبر BullMQ (بتوقيت UTC).
  • كلّ نبضة تولّد بثّاً جديداً من قالب + قائمة، مع احترام المنسحبين.
  • إعدادات جاهزة + cron خام بخمسة حقول؛ مطابقة عند الإقلاع.

1.8 · صندوق وارد ثنائي الاتجاه (المرحلة الرابعة — مكتملة)

  • نموذجا Conversation/Message؛ التقاط الوارد لِنصّ، صورة، مستند، صوت، فيديو، ملصق، تفاعلي، تفاعل (reaction)، موقع — عدم تكرار عبر wamid.
  • تتبّع نافذة الخدمة لمدّة 24 ساعة؛ صادر نصّي + مرفقات داخل النافذة.
  • عرض الوسائط عبر وسيط آمن للرمز (/api/media/:id)؛ إيصالات قراءة (أفضل جهد)؛ واجهة حيّة بجزأين /inbox.

1.9 · الانسحاب والامتثال

  • STOP ← OptOut (فريد لكلّ عميل+هاتف)؛ يُستثنى من كلّ البثّ المستقبلي.
  • الموافقة على الاشتراك مأخوذة من CSV (غير مفروضة بنيوياً بعد ← §2.11).

1.10 · إعداد واتساب بدون كود

  • لكلّ عميل: معرّف رقم الهاتف، معرّف WABA، معرّف التطبيق، الرمز، سرّ التطبيق، رمز التحقّق، إصدار API.
  • اختبار الاتصال؛ رابط webhook + رمز التحقّق؛ الإعدادات المحفوظة تتجاوز البيئة دون إعادة نشر.
  • وُضِّحت تسميات الحقول لتفادي الخلط بين معرّف WABA ومعرّف محفظة الأعمال.

1.11 · المنصّة والتشغيل

  • نقطة فحص صحّة؛ ترويسات أمان؛ صورة Docker متعدّدة المراحل بمستخدم غير جذري مع فحص صحّة.
  • ترحيلات SQL مكتوبة يدوياً 0001 → 0015 تُطبَّق عند الإقلاع؛ verify.sh دون اتصال؛ اختبار حِمل webhook بـ k6؛ شرح تفاعلي ثنائي اللغة على /tutorial.html.

ثانياً.الإصدار الثاني — ميزات المرحلة الثانية

كلّ ميزة تذكر: ما هي · كيف تعمل · نموذج البيانات · الاعتماديات · الجهد · معيار القبول. الجهد مقدّر وفق المكدّس الحالي.

★ 2.1 · صندوق وارد متعدّد القنوات (واتساب + رسائل إنستغرام + ماسنجر)

ما هي: توسعة الصندوق ثنائي الاتجاه إلى ما وراء واتساب ليشمل كلّ أسطح مراسلة Meta في عرض موحَّد للوكلاء.

كيف: إضافة قيمة channel إلى Conversation/Message؛ تعميم معالج الـ webhook (التوجيه حسب object + الأصل المتّصل) ومحوِّل إرسال رفيع لكلّ قناة فوق whatsapp.ts؛ مرشّح قناة + شارة في /inbox.

البيانات: Conversation.channel، Message.channel، ChannelConnection. الاعتماديات: أذونات مراسلة إنستغرام + ماسنجر.

القبول: ظهور رسالة إنستغرام ورسالة ماسنجر بجانب واتساب، قابلة للردّ، مع احترام نافذة كلّ قناة.

الجهد: كبيرالملاءمة: عاليةطلبك الرئيسي

★ 2.2 · تسجيل Meta المدمج (ربط واتساب بنقرة واحدة)

ما هي: استبدال الإدخال اليدوي لمعرّف الهاتف/WABA/الرمز بتدفّق تسجيل Meta المدمج عبر OAuth — زرّ «اربط واتساب».

كيف: فتح نافذة التسجيل المدمج، تبادل الرمز على الخادم للحصول على رمز مستخدم-نظام طويل العمر، اكتشاف معرّفات WABA والهاتف تلقائياً، وحفظها في إعداد العميل.

لماذا: يزيل مباشرةً أكبر عائق في الإعداد (الخلط بين معرّف WABA ومحفظة الأعمال + نطاقات الرمز). يتيح إعداداً ذاتياً حقيقياً.

البيانات: WhatsAppConfig.wabaAutoConnected/tokenExpiresAt. الاعتماديات: إعداد مزوّد تقني + مراجعة التطبيق.

الجهد: متوسّطالملاءمة: عاليةيُنصح به أولاً

★ 2.3 · تعاون الفريق في الصندوق

ما هي: تحويل الصندوق إلى مكتب دعم مشترك حقيقي.

كيف: حالة المحادثة (OPEN/PENDING/CLOSED)، إسناد لوكيل + مرشّحات، ملاحظات داخلية + إشارات @، ردود جاهزة، مؤقّتات SLA.

البيانات: Conversation.status/assigneeId، InternalNote، CannedReply.

الجهد: متوسّطالملاءمة: عالية

2.4 · مساعد الذكاء الاصطناعي (مدعوم بـ Claude)

ما هي: طبقة ذكاء فوق المحادثات والمحتوى — ردود مقترَحة، تلخيص المحادثة، ترجمة عربي↔إنجليزي، وسم النيّة/المشاعر، إجابة تلقائية للأسئلة الشائعة من قاعدة معرفة لكلّ عميل، وصياغة نصوص البثّ.

كيف: نداءات على الخادم لأحدث طُرز Claude عبر Anthropic SDK؛ قاعدة معرفة لكلّ عميل تُسترجَع (RAG)؛ الوكيل في الحلقة افتراضياً مع وضع ردّ آلي اختياري.

البيانات: KnowledgeDoc، Message.aiTags، Conversation.aiSummary.

الجهد: متوسّطثنائي اللغة عربي/إنجليزي

2.5 · الأتمتة والردود التلقائية و Flows

ما هي: صدّ وجذب عملاء على مدار الساعة — رسائل ساعات العمل والغياب، ردود تلقائية بالكلمات المفتاحية، مُنشئ تدفّقات بسيط بدون كود، WhatsApp Flows الأصلية (نماذج داخل المحادثة)، وإعادة فتح النافذة عبر قالب.

كيف: محرّك قواعد في العامل على الأحداث الواردة؛ تُرسَل الـ Flows إلى Meta كالقوالب.

البيانات: AutomationRule، Flow.

الجهد: كبير

2.6 · ملفّ جهة الاتصال 360 / CRM مصغّر

ما هي: ملفّ موحَّد لجهة الاتصال — خطّ زمني عبر القنوات (محادثات + بثّ)، وسوم، محرّر سمات مخصّصة، ملاحظات، حالة الموافقة والنافذة.

البيانات: Contact.tags، ContactNote.

الجهد: متوسّط

2.7 · التقسيم الديناميكي واختبار A/B وتوقيت الإرسال

ما هي: شرائح ديناميكية (عضوية تلقائية حسب قواعد)، اختبار A/B للبثّ (تقسيم + مقارنة)، تحكّم بمعدّل التوقيت ولاحقاً تحسين حسب المنطقة الزمنية لكلّ جهة.

البيانات: Segment، Broadcast.variantOf.

الجهد: متوسّط

2.8 · النموّ وجذب العملاء المحتملين

ما هي: رابط wa.me + مولّد رمز QR (مُعبّأ ومُتتبَّع)، أداة دردشة قابلة للتضمين في الموقع، وعزو إعلانات النقر-إلى-واتساب.

البيانات: Contact.source، Conversation.referral.

الجهد: متوسّط

2.9 · التحليلات وتتبّع الروابط وقابلية التسليم

ما هي: تتبّع نقرات الروابط لكلّ مستلِم (مختصِر روابط)، تقارير تحويل/عائد، تقارير قابلة للتصدير، لوحة جودة الرقم وحدود المراسلة مع إيقاف تلقائي عند هبوط الجودة، وأداء القوالب.

البيانات: ShortLink، LinkClick، QualitySnapshot.

الجهد: متوسّط

2.10 · التجارة

ما هي: رسائل كتالوج/منتج/متعدّد المنتجات في واتساب، إشعارات الطلب والشحن، تدفّقات السلّة المهجورة، روابط الدفع.

البيانات: Catalog، Product، Order. الاعتماديات: كتالوج Meta Commerce + مزوّد دفع.

الجهد: كبير

2.11 · الحوكمة: الأذونات وسجلّ التدقيق والموافقة

ما هي: أذونات لكلّ إجراء (تتجاوز المصادقة فقط اليوم)، سجلّ تدقيق بعزو الفاعل على البثّ/الحذف/الإعداد، موافقة مزدوجة، سجلّ موافقة + تصدير/حذف بيانات وفق GDPR.

البيانات: AuditEvent، ConsentRecord، Role/Permission أغنى.

الجهد: متوسّطيسدّ ثغرات الإصدار الأول

2.12 · الفوترة والخدمة الذاتية (مسار SaaS)

ما هي: قياس استهلاك (قائم على المحادثات، يحاكي تسعير Meta)، خطط/حصص، فوترة Stripe، ترقية داخل التطبيق، لوحة استهلاك لكلّ عميل. يتكامل مع التسجيل المدمج لإعداد ذاتي كامل.

البيانات: Subscription، UsageRecord، Plan. الاعتماديات: Stripe.

الجهد: كبير

2.13 · التكاملات وواجهة API العامّة

ما هي: webhooks صادرة (أحداث الرسائل/البثّ)، تطبيق Zapier/Make، واجهة REST عامّة موثّقة بمفاتيح لكلّ عميل، ومزامنة CRM/جداول.

البيانات: ApiKey، OutboundWebhook.

الجهد: متوسّط

رابعاً.خارطة الطريق والتسلسل

  1. التسجيل المدمج (§2.2) — صغير، يزيل أكبر عائق في الإعداد، ويفتح الخدمة الذاتية.
  2. الصندوق متعدّد القنوات (§2.1) — القدرة الرائدة للمرحلة الثانية.
  3. تعاون الفريق (§2.3) — مبني فوق الصندوق الموحَّد.
  4. مساعد الذكاء (§2.4) + الأتمتة/Flows (§2.5) — قيمة متراكمة بعد توحيد القنوات.
  5. التحقيق المالي: الحوكمة (§2.11) + الفوترة (§2.12) لِـ SaaS، أو التجارة (§2.10) للتجزئة.

خامساً.المتطلبات غير الوظيفية

  • الأمان: إبقاء middleware.ts آمناً للحافة؛ التحقّق بـ Zod من كلّ الحمولات/الـ webhooks الجديدة؛ توسعة التحقّق من التوقيع لكلّ عميل إلى كلّ قناة؛ الأسرار في إعداد كلّ عميل دون إيداعها في المستودع.
  • تعدّد العملاء: كلّ كيان جديد يحمل clientId؛ العزل دائماً عبر محلّل العملاء؛ احترام تجاوز العميل النشط للمشرف العام.
  • قابلية التسليم: إبقاء WA_MPS × workers ≤ فئة Meta؛ مراقبة الجودة لتفادي التقييد/الحظر.
  • الامتثال: موافقة مزدوجة + سجلّات موافقة قبل توسيع الصادر؛ احترام الانسحاب عبر كلّ القنوات.
  • بوّابة الإنجاز (ثابتة): typecheck · test · build كلّها خضراء؛ اختبارات موجبة + سالبة للمنطق الجديد؛ اختبارات طرف-لطرف للمسارات الجديدة. تستمرّ الترحيلات من 0016.

سادساً.القيود المعروفة والبنود المفتوحة

  • التفويض مقتصر غالباً على المصادقة؛ فقط /api/users محميّ بالأدوار ← §2.11 الأذونات.
  • لا عزو فاعل / سجلّ تدقيق على البثّ أو الحذف ← §2.11 التدقيق.
  • الموافقة على الاشتراك مأخوذة من CSV وغير مفروضة بنيوياً ← §2.11 الموافقة.
  • حذف جهة الاتصال بلا أثر عند وجود سجلّ بثّ (FK RESTRICT).
  • إبطال رمز الوصول يتأخّر ≤15 دقيقة بالتصميم؛ تحديد معدّل الدخول يفشل مفتوحاً.
  • تحديد المعدّل لكلّ عامل: عدّة عمّال قد يتجاوزون فئة Meta — أبقِ WA_MPS × workers ≤ الفئة.
  • التحقّق الحيّ: الاتصال + إرسال/مزامنة القوالب مُتحقَّق منها؛ دورة بثّ كاملة + صندوق وارد على رقم حقيقي هي الخطوة التالية مباشرةً (VERIFY.md).
يبقى ما تبقّى من المرحلة الخامسة (القوالب الغنية) قائماً: عرض محدّد المدّة ← مصادقة/OTP ← كتالوج ← Flows (الكتالوج و Flows مدمجان الآن في §2.10 / §2.5 من الإصدار الثاني).
